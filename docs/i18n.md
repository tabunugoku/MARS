# Languages (Japanese and English)

ComiNavi's interface is in Japanese and English. Japanese is the source
language: every string is written in Japanese first, and English must have
the same keys (the type checker enforces it).

## How the language is chosen

1. The user's own choice, `User.locale` (`"ja"`, `"en"`, or `""` to follow
   the browser), set in 設定 > アカウント.
2. Otherwise the browser: `navigator.languages`, first tag starting with
   `ja` or `en`.
3. Otherwise Japanese.

Before sign-in (the /login page) there is no user, so the web app uses the
last language it used on this browser (`localStorage["cominavi.locale"]`),
then the browser, then Japanese.

The web app sends the resolved language on every API call as
`Accept-Language: ja` or `Accept-Language: en`.

## Web (`web/src/i18n/`)

No i18n library: a small module, so the initial bundle stays under budget.

- **Messages live next to the code that uses them**, in one
  `defineMessages` call per file or folder. Both languages sit in the same
  object, so a lazy screen's strings load with its chunk and nothing is
  fetched when the language changes.

  ```ts
  import { defineMessages, useT } from "@/i18n";

  const m = defineMessages({
    ja: {
      title: "ライブラリ",
      books: ({ n }) => `${n} 冊`,
      deleted: "{name} を削除しました",
    },
    en: {
      title: "Library",
      books: ({ n }) => (n === 1 ? "1 book" : `${n} books`),
      deleted: "Deleted {name}",
    },
  });

  function Screen() {
    const t = useT(m);
    return <h1>{t("title")}</h1>; // t("books", { n: 3 }), t("deleted", { name })
  }
  ```

- A message is a string (with `{param}` placeholders) or a function of the
  params (for plurals and anything a placeholder cannot say). The `en` side
  must have exactly the `ja` keys.
- Outside components (label maps, toasts fired from plain functions), use
  `translate(m, key, params)`, which reads the current language. Label maps
  such as `DIRECTION_LABEL` become functions or are looked up at render
  time, so they follow a language change.
- `useLocale()` returns `"ja" | "en"`; `intlLocale()` returns `"ja-JP"` or
  `"en-US"` for `Intl` and `toLocaleString`. Dates and numbers always go
  through these, never a hard-coded `"ja-JP"`.
- Changing the language re-renders the app without a reload.
- Keys are short camelCase names, local to their `defineMessages` call.
- The PWA manifest stays Japanese.

### English copy

Plain, short, sentence case, no full stops on labels and buttons. Keep the
Japanese UI's tone: direct, no exclamation marks. Prefer the words Komga
users know: Library, Series, Book, Collection, Read list, Mark as read.

## Server

- Every error response is `{ "code": "...", "message": "..." }`. `code` is a
  stable dotted name (`not_found.book`, `bad_request.password_too_short`,
  `forbidden.download`). `message` is in the request's language:
  `Accept-Language` starting with `en` gives English; anything else,
  including no header, gives Japanese (so existing tests keep passing).
- Messages live in one catalog (`server/internal/httpapi/messages.go`):
  code → Japanese and English text, with `%s`/`%d` arguments where needed.
  Handlers pass the code and arguments; they never write text inline.
- Reader-facing text in data fields (`Library.watchError`,
  `Book.mediaError`) follows the same language.
- Log messages stay in English.

## Checks

- `npm run i18n:check` (in `web/`, run in CI) fails when a `.ts`/`.tsx`
  file under `web/src` has Japanese text outside an `ja:` block of a
  `defineMessages` call, a comment, or the files it excludes (`src/mock/`,
  `src/api/mock.ts`, `src/i18n/`).
